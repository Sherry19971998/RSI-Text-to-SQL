结论：Text-to-SQL 里“生成→反馈→修改”的工作很多，而且已经分化成四条路线：提示式自我修正（2023 起）、训练专门的批改/修正模型（2023 起）、用执行反馈做多轮强化学习（2025 起集中出现）、人类自然语言反馈（2020 起）。因此“这类方法还没有做 Text-to-SQL”不成立。

0｜通用背景：Self-Refine 与 Huang 等之后的三条修补路线

非 SQL 实验

Huang 等指出“没有外部信号时自我修正无效”。后续工作分别从三个方向回应：加入外部工具反馈、定位错误、用强化学习直接训练修正能力。

论文有无训练解决什么问题主要贡献与关键步骤核心公式与说明优势与比较对象局限与适用边界
CRITIC2023.05 首次提交Gou et al., ICLR 2024 · 2305.11738问答 / 数学程序 / 去毒，非 SQL 否只用提示和外部工具，不更新参数 模型自我评价不可靠；人类改稿时会借助搜索、代码解释器等工具核查。 ① 生成初稿；② 调用工具（搜索、解释器、毒性 API）核查指定方面，生成批评 ci；③ 依据批评修改；④ 重复“核查→修改”直到满足停止条件。 流程概括（按作者记号）℘：提示示例；𝒯：工具；ci：基于工具结果的批评。 相对 CoT（ChatGPT，F1）：AmbigNQ 64.3→74.9；HotpotQA 42.8→52.9。 相对完整 CRITIC：去掉工具只剩 67.3 / 46.1，大部分收益来自外部工具；依赖可用的工具与调用成本。
LLMs cannot find reasoning errors, but can correct them2023.11 首次提交Tyen et al., ACL 2024 Findings · 2311.08516BIG-Bench 推理任务，非 SQL 部分主实验只用提示；另训练了一个小型找错分类器作初步验证 自我修正失败，是因为模型“改不对”，还是“找不到错”？ ① 构建 BIG-Bench Mistake：人工标注思维链中第一个逻辑错误的位置；② 测 5 个模型的找错能力；③ 给定真实错误位置，回溯重写该步之后的内容。 规则概括（无核心公式）回溯：丢弃标出的错误步及之后内容，重新采样该步再继续生成；用随机位置作对照。 相对随机位置回溯：给定真实错误位置时收益明显更大；例：word sorting 中 23.53% 原本错的轨迹被改对。 找错是瓶颈：GPT-4 找错准确率仅 52.87；同时 11.11% 原本对的轨迹被改错；任务为人工构造，作者承认不够真实。
SCoRe2024.09 首次提交Kumar et al., 2024, arXiv · 2409.12917数学 MATH / 代码 HumanEval，非 SQL 是两阶段多轮在线 RL，训练修正能力 用离线修正轨迹做 SFT 学不会真正的自我修正：模型要么不改，要么分布漂移。 ① 第一阶段：约束第一次回答接近原模型，同时优化第二次回答；② 第二阶段：多轮在线 RL，用奖励塑形鼓励“第二次比第一次好”；③ 全部用模型自己生成的数据。 作者原式（第二阶段奖励塑形）只奖励“从错改对”的进步，惩罚“从对改错”。 相对原 Gemini 模型：自我修正增益 Δ(t1,t2) 在 MATH 上 +15.6，在 HumanEval 上 +9.1（绝对值）。 只训练两轮修正；需要可验证的正确性奖励；论文同时报告 SFT 方法会“学会不改”。

比较结论

  • 三篇都承认 Huang 的结论：没有外部信号时自我修正难以奏效。
  • 补救方式不同：CRITIC 引入工具反馈；Tyen 说明瓶颈在“找错”；SCoRe 用 RL 直接训练修正能力。

需要继续验证

  • SQL 的执行器相当于 CRITIC 的“工具”，但执行成功不等于结果正确，反馈强度弱于单元测试。
  • SCoRe 式的“只奖励进步”能否用于 SQL 多轮修正？见第 3 组。

1｜Text-to-SQL：提示式自我修正（不训练）

Text-to-SQL

直接对应 Self-Refine：同一模型或多个智能体根据执行结果、报错或总结出的指南修改 SQL。

论文有无训练解决什么问题主要贡献与关键步骤核心公式与说明优势与比较对象局限与适用边界
DIN-SQL2023.04 首次提交Pourreza & Rafiei, NeurIPS 2023 · 2304.11015Spider / BIRD 否少样本与零样本提示 少样本提示在复杂 SQL 上明显落后于微调模型；生成的 SQL 常缺 DESC、DISTINCT、聚合函数等。 ① 分解：schema linking→难度分类→按难度生成；② 自我修正模块：只给出生成的 SQL，零样本要求模型修 bug；③ 两种修正提示：generic（明说“BUGGY SQL”）与 gentle（不假设有错，只提示检查哪些子句）。 规则概括（无核心公式）修正提示的选择：CodeX 用 generic 更好，GPT-4 用 gentle 更好。 相对当时 SOTA：Spider 测试集 EX 85.3（GPT-4）；BIRD 测试集 55.9。 修正针对“小错误”（关键词缺漏），不处理语义错误；摘要中未单独报告修正模块的贡献〔分析：需查附录消融〕。
Self-Debug2023.04 首次提交X. Chen et al., 2023, arXiv · 2304.05128Spider（另有代码翻译、MBPP） 否少样本提示 复杂程序很难一次写对；Spider 没有单元测试，模型难以判断 SQL 是否正确。 ① 生成 SQL 并执行；② “橡皮鸭调试”：总结问题、推断应返回几列，逐行解释 SQL；③ 依据解释和执行结果判断对错并修改。 流程概括反馈三档：simple（只说对/错）、unit test、explanation（自我解释）。Spider 上只给 simple 反馈不足以判断正确性。 相对不调试的基线：Spider 提升 2–3 个点，最难一档提升 9 个点；能匹敌多采样 10 倍候选的基线。 GPT-3.5 / GPT-4 上少样本调试提示收益不明显；没有执行正确性信号时，修正依赖模型自我解释的质量。
MAGIC2024.06 首次提交Askari et al., AAAI 2025 · 2406.12692BIRD / Spider 否智能体在训练集失败案例上生成指南，不更新模型参数 自我修正依赖专家手写的“修正指南”，费时，且覆盖不了模型的全部错误模式。 ① 在训练集上收集某方法的失败案例；② 管理者、反馈、修正三个智能体循环：反馈智能体解释错误，修正智能体据此改写并执行验证；③ 每累计若干条反馈，汇总成可复用的修正指南；④ 测试时把指南放进修正提示。 规则概括（无核心公式）指南按错误类型组织（如 LIMIT 遗漏），测试时让模型先自问再修改。 相对专家手写指南：自动指南效果更好，且修正过程可解释（原文主表）。 指南生成需要训练集上的标准 SQL；指南随基础方法而定，换生成方法需重新生成〔分析〕。
ReFoRCE2025.02 首次提交Deng et al., 2025, arXiv · 2502.00675Spider 2.0（企业级、多方言） 否提示式智能体工作流 企业库 schema 超长（千列以上）、方言多样，单次生成常有语法与语义错误。 ① 压缩数据库信息（按模式分组表、LLM 引导 schema linking）；② 依据执行反馈自我修正，最多 5 轮；③ 多数投票选高置信答案，低置信题延后；④ 对延后题做执行反馈引导的列探索。 流程概括修正平均 1.69 次 LLM/数据库调用、约 15.4K token（不含列探索）。 相对 Spider 2.0 已有方法：Snow 35.83、Lite 36.56，当时榜首。 消融（o3）：去掉 schema 压缩 −3.65、去掉列探索 −2.56、去掉投票 −2.01；没有单独“去掉自我修正”的消融。

比较结论

  • SQL 的提示式修正普遍借助执行器：报错、执行结果、或在训练集失败案例上总结出的指南。
  • DIN-SQL 与 ReFoRCE 都没有把“修正”单独拆出来量化，收益常与其他模块混在一起。

需要继续验证

  • 去掉修正模块单独看，提示式修正对强模型还剩多少收益？第 5 组的评估工作给出了部分答案。
  • 修正会不会把原本正确的 SQL 改错？这几篇大多未报告改错率。

2｜Text-to-SQL：训练专门的批改或修正模型

Text-to-SQL

对应 Tyen 等“找错是瓶颈”：把检测与批改单独训练成模型，再把信号交给生成模型修改。

论文有无训练解决什么问题主要贡献与关键步骤核心公式与说明优势与比较对象局限与适用边界
SQLCritic2025.03 首次提交J. RetrySQL2025.07 首次提交Rączkowska et al., AAAI 2026 · 2507.02529BIRD / Spider 是用重试数据继续预训练生成模型 自我修正策略很少被训练进 SQL 专用的开源生成模型。 ① 用 GPT-4o 为参考 SQL 生成推理步骤；② 随机替换某些步骤为错误步骤，其后插入 [BACK] 和正确步骤，构成重试数据；③ 用重试数据继续预训练开源代码模型。 规则概括s1…s′k [BACK] sk…sn：错误步之后紧跟回退标记和正确步。 相对不含重试数据的预训练：整体执行指标最多 +4 点，困难题 +9 点。 错误是人为随机构造，不是模型真实犯的错；训练数据只来自 BIRD/Spider，规模有限（作者自述）。

比较结论

  • SQLCritic、SHARE、ErrorLLM 都直接复现了 Huang 的现象：提示式或内在自我修正在 BIRD 上会降分或几乎不变。
  • 有效的做法都是把“找错”交给专门训练的模型，与 Tyen 等的结论一致。

3｜Text-to-SQL：用执行反馈训练多轮修正（DPO / RL）

Text-to-SQL

对应 SCoRe：不再只靠提示，而是把“执行→看结果→修改”训练进模型。2025 年下半年起集中出现，与我们课题最接近。

论文有无训练解决什么问题主要贡献与关键步骤核心公式与说明优势与比较对象局限与适用边界
ExCoT2025.03 首次提交Zhai et al., 2025, arXiv · 2503.19988BIRD / Spider 是迭代离线＋在线 DPO 零样本 CoT 对 SQL 帮助小；不带 CoT 的 DPO 提升也有限。 ① 采样带 CoT 的 SQL，在本地 SQLite 执行，与标准结果比对标记对错；② 选编辑距离最大的“对–错”对做离线 DPO；③ 再用当前模型生成做在线 DPO，迭代多轮。 本次整理：标准 DPO；正负例只由执行结果决定不需要奖励模型或人工偏好。 相对原模型（LLaMA-3 70B）：BIRD dev 57.37→68.51；Spider test 78.81→86.59。 反馈用于构造训练对，不是推理时的多轮修改；复杂 schema 与领域惯例仍难（作者自述）。

MTIR-SQL2025.10 首次提交Xu et al., 2025, arXiv · 2510.25510BIRD / Spider 是多轮工具 GRPO RL 方法多依赖静态执行反馈，无法在推理中实时纠错；多轮工具 RL 训练不稳定。 ① 每步推理都可调用数据库获得执行反馈；② GRPO 扩展到多轮工具交互；③ 加轨迹过滤、去掉 KL 约束以稳定训练。 标准 GRPO 组内优势（作者在此基础上修改）组内全对或全错时优势为 0，不产生学习信号。 相对基线（Qwen3-4B）：BIRD dev 64.4（绝对 +16），Spider dev 84.6，与 7B 代码模型相当。 去掉 KL 后模型可能远离初始分布，作者用轨迹过滤缓解；只在 4B 级别验证。
SQL-Trail2026.01 首次提交Hua et al., 2026, arXiv · 2601.17699Spider / BIRD（BIRD 作分布外） 是多轮 RL（约 1.9K 条训练数据） 单次生成范式缺少人类专家常用的迭代推理、schema 探索和纠错。 ① 智能体与数据库多轮交互，用执行反馈迭代修改；② 按题目难度自适应分配交互轮数；③ 复合奖励面板同时奖励正确性与高效探索。 规则概括轮数预算随难度变化：简单题少轮、难题多轮，避免“过度思考”。 相对 Sonnet-3.7（同评测）：7B 在 BIRD dev 上 60.1（贪心）/ 64.2（投票），高 1.6 / 4.1；只用 1,873 条训练数据，比单轮 RL 数据效率高 7–18 倍。 需要可交互的执行环境；多轮交互增加延迟与成本；BIRD 未参与训练（作者自述）。
ReToolSQL2026.08 首次提交Kakkar et al., 2026, arXiv · 2608.27796BIRD 是SFT＋多轮智能体强化微调 多数执行反馈 RL 仍把生成当单轮任务，模型学不到从错误中恢复。 ① SFT：用经执行验证、拒绝采样得到的“特权教师”轨迹预热；② 多轮工具使用轨迹上做智能体强化微调（RFT）；③ 学会何时验证、取什么证据、如何根据执行反馈修 SQL。 规则概括两阶段分工：SFT 扩大 pass@k 覆盖（难题上能做对的题变多），RFT 把它转成单次准确率。 相对单独 RFT（Gemma 4 31B）：RFT 73.66；SFT→RFT 74.32（单次）/ 74.77（自洽），发表时 BIRD 单模型榜首。 31B 级别模型，训练成本高；特权教师轨迹需要额外信息构造〔分析〕。

比较结论

  • SQL 里已有多篇“用执行反馈训练多轮修正”的工作，相当于 SCoRe 在 SQL 上的对应物。
  • ReToolSQL 明确区分了“扩大覆盖率”和“提高单次准确率”两种作用，与我们的覆盖率假设直接相关。

需要继续验证〔分析〕

  • 这些工作都在 RL 中保留全部有奖励的轨迹；“多轮自训练时该保留哪些修正轨迹”在本次阅读的论文里没有被单独研究，但需更完整检索才能确认。
  • 多轮修正的收益是否也伴随 SCoRe 所说的“学会不改”？多数论文未报告修正前后的翻转率（错→对、对→错）。

SPLASH2020.05 首次提交Elgohary et al., ACL 2020 · 2005.02539Spider 问题 是训练修正模型（基线） 语义解析通常是一次性翻译；用户发现错误后无法纠正系统。 ① 用 Spider 问题生成错误 SQL；② 把 SQL 解释成自然语言步骤给众包工人看；③ 不懂 SQL 的工人用自然语言写反馈；④ 训练“问题＋错误 SQL＋解释＋反馈→正确 SQL”的修正模型。 本次整理：任务定义q：问题；s：schema；y0：错误 SQL；e：系统解释；fb：用户反馈。 相对不用反馈：加入反馈能显著提升修正；人类修正准确率估计为 81.5%。 最好的模型修正准确率只有 25.1%，与人类差距大；对 EditSQL 自身的错误，修正准确率 14.6%。
NL-EDIT2021.03 首次提交Elgohary et al., NAACL 2021 · 2103.14540SPLASH 是训练编辑生成模型 直接重新生成整条 SQL 难以准确落实用户反馈。 ① 把反馈解读为一串编辑操作（替换列、增删 WHERE 条件、去掉 LIMIT 等）；② 把编辑作用在原 SQL 上；③ 用模板合成反馈数据扩充训练。 本次整理输出的是编辑序列，而不是整条新 SQL。 相对 EditSQL+Feedback：修正准确率 25.16→41.17；一轮修正最多让已有解析器提升 20%。 需要修改的编辑超过 2 处时准确率显著下降；只考察一轮反馈。

比较结论

  • 人类反馈是最强的外部信号，但模型利用它的能力远低于人类（25.1 vs 81.5）。
  • 以编辑而非重写来修正，更容易落实反馈。

需要继续验证

  • 这条线早于大模型；用大模型模拟用户反馈（如 BIRD-INTERACT 的模拟用户）能否替代人工？

Elgohary et al. (2020)；Elgohary et al. (2021)。

总表：第 5 页两篇的结论，在 SQL 中的对应证据

第 5 页论文的结论SQL 中的对应证据（论文结论）对我们课题的含义〔分析〕
Self-Refine：同一模型写稿→自评→修改能提升多类任务DIN-SQL、Self-Debug、MAGIC、ReFoRCE 把这一流程用于 SQL；有效时都借助了执行结果、报错或从训练集总结的指南（第 1 组）。SQL 的“反馈”主要来自执行器；纯自评版本不应作为主要证据。
Huang 等：没有外部信号时，自我修正无效甚至有害GPT-4o 在 BIRD 上内在自我修正 55.87→55.28（SHARE）；整体式批评 49.87→45.12（SQLCritic）；已有修复误修复多（MapleDoctor）；在强底座上多数修正方法降分（ErrorLLM）。结论在 SQL 中成立；评估修正时应报告“对→错”的翻转率，而不只是净准确率。
后续通用工作：外部工具、找错、RL 训练SQL 中分别对应：执行反馈修正（第 1、5 组）、专门的批改模型（第 2 组）、多轮执行反馈 RL（第 3 组）。与我们最近的是第 3 组；本次阅读中未见研究“多轮自训练应保留哪些修正轨迹”的工作，需更完整检索。
