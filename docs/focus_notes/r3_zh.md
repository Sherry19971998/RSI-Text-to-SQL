# R³-SQL（arXiv 2604.25325）

**一句话：** 把执行结果相同的候选 SQL 分成一组，对组排序；候选池里多半没有正确答案时重新采样。BIRD-dev EX 达到 75.03，是公开模型规模的方法中最好的。

**怎么做：**
- 用 Arctic-Text2SQL-R1-32B（T=0.8）生成 32 条候选，执行后按结果分组。
- 按两两比较的胜场数（R³-7B）给组排序；胜场相同时，看"组大小 × 组内最佳 pointwise 排名"。
- 7B agent 判断池中没有正确 SQL 时，重新采样 1,024 条，保留前 32 条。
- R³-7B 用 GRPO 训练；调换候选顺序后判断不变，额外给奖励。

**关键结果：**

| BIRD-dev / 5 个基准，32B 生成器 | 数值 |
|---|---|
| BIRD-dev EX：R³-SQL vs CHASE-SQL | 75.03 vs 73.34 |
| 5 个基准平均 EX vs 最强基线 | 70.65 vs 68.70 |
| 平均候选召回率：有 / 无重采样 | 82.72 / 78.80 |
| 去掉重采样的 BIRD-dev EX | 74.25 |

**关键公式：**
- r_point(g) = |g| · max_{s∈g} RR_s：先按胜场数 r_list 排序，平局时用 r_point，组越大、组内最好的 SQL 排名越靠前，就排得越前。
- 若 f(S)=0 则 S ← S̃，否则保留 S：只有 agent 判断池中没有正确 SQL 时才换池。

**局限：**
- pointwise ranker 只在 BIRD 上训练，跨领域时会引入噪声。
- 开销大：8×H200 上 1.56 秒/题，每道题最多再采 1,024 条。

**对我们项目的启示：**
- 重采样提升的是覆盖，和我们"保住覆盖（frontier）很重要"的发现一致。
- 可以按执行结果给正确轨迹分组，让 rare_first 和 frontier 统计的是真正不同的答案。
- 他们改进的是推理时的选择，我们改进的是训练（53.06 → 59.34），两者可以叠加。
