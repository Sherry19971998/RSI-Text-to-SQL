# 新方向：Text-to-SQL “生成→反馈→迭代修改”为什么失败（2026-10-31）

## 和文献页主题的关系

文献页（https://claude.ai/artifact/YV1ZrnFL8n2x6uNuAgQjZw）的主题是“生成→反馈→迭代修改”。新课题研究的是同一个循环：模型先写 SQL，再根据反馈修改，最多改 3 轮。只做推理，不训练。

研究问题：这个循环失败时，问题出在哪一步——
- 找错：判断这条 SQL 是否有错；
- 定位：找出错在哪个子句；
- 改写：知道错在哪以后能否改对。

另外两个问题：反馈里放什么最有用；在相同算力下，修改是否比重新采样更划算。

## 精读的三篇论文

### Lin et al. 2026, *Are These Modules Worth Their Cost?*（2608.28432）

**做了什么**
- 统一实现了 17 种上下文学习流水线配置，在 BIRD dev 上测了 4 个底座：GPT-4o-mini、Gemini-2.5-Flash、DeepSeek-V4-Flash（推理模型）、GPT-5.4。
- 每次只替换一个模块，用 McNemar 检验显著性。

**和我们相关的事实**
- 他们的 R1（执行反馈修正）**只在执行报错或返回 0 行时才触发**，所以平均成本很低。
  - 在 4 个底座上的收益为 +1.83 到 +4.89 个点，每涨 1 个点的成本低于 0.30 美元。
  - 例如 GPT-4o-mini 从 49.74 到 54.63；GPT-5.4 从 61.28 到 63.30。
- R2（不执行、只靠提示自查）在推理底座上不显著（+0.26），成本高得多。
- R3（多角色、带执行反馈）在 4 个底座上都有提升，但成本高一到两个数量级。
- 作者的解释：执行反馈提供了生成时没有的信息，而提示内的自查只是让模型再说一遍它本来就能说的。
- 候选选择受候选池上限限制：N=5 的最佳选择器离 oracle 上限还差最多 5.74 个点。

**没有做的（我们的空间）**
- 只报净准确率，没有报告错→对和对→错的翻转率。
- R1 按设计碰不到"能执行、返回了行、但结果错"的 SQL（静默错误）。这类 SQL 占错误的多少、能不能修，都没有回答。
- 修改和采样只在 N=5 这一个点上比较，没有画随算力变化的曲线，也没有试混合方案。
- 只用了 API 模型，没有开源模型。没有区分找错、定位、改写三步。

### ACTS-SQL（2608.15145，PVLDB 投稿）

**做了什么**
- 不训练的树状修正框架：先写修正计划，再分支探索不同解释，必要时回溯。
- 用到的工具：歧义检测、查看列值、执行 SQL、按子句拆分并修复语法错误。

**结果**
- 在 BIRD-Critic 上比此前最好方法高 9.42%。
- 部署在火山引擎的日志查询服务（TLS）上，GPT-5 从 36.77% 提高到 53.61%。
- 消融：去掉执行工具比去掉歧义检测掉得更多。

**和我们相关的观察**
- 作者称，线性修改会被第一次的错误假设"锁住"：后续轮次只在同一种理解里做局部修改，不会回头换理解。
- 这给 X3 一个可检验的假设：重新采样比沿着原 SQL 修改更容易跳出这种锁定。

**没有做的**
- 任务是"修复用户报告的错误 SQL"（BIRD-Critic），不是自己生成再修改。
- 没有翻转率，没有找错/定位/改写的分解，没有和采样做等算力比较。
- 文中提到 Qr-Hint，它用参考答案给写错 SQL 的人类学习者提示错误位置，和我们的 oracle_clause 最接近。**还没读，要补。**

### Reflective Reasoning for SQL Generation（2601.06678）

**做了什么**
- 把生成拆成几个阶段：schema、取值、聚合、谓词、SQL。
- 批改器把错误定位到某一阶段，然后修改该阶段的提示，而不是直接改这一条 SQL。
- 不用标准 SQL，用解释器检查加 LLM 语义检查做裁判。

**和我们相关的结果**
- 反馈粒度（GPT-4o）：只说对/错为 BIRD 61.0；指出具体类别和片段为 65.2。
  - 这些反馈来自他们自己的批改器，**不是 oracle**，所以分不清"定位信息有用"和"批改器判断准"这两个因素。
- 过度修改：8B 模型（Qwen3-8B、Llama-3.1-8B）前 3 轮上涨，第 3 到第 6 轮下降 5–8 个点。作者观察到早期引入的幻觉表或谓词会被后续轮次"锁住"。
- 数值没有方差或显著性检验；Spider 上的数字偏高，和其他论文不可直接比较。

**没有做的**
- 没有翻转率，没有 oracle 对照，也没有等算力比较。

### 补充检索到的相关工作
- NL2SQL-Bugs（2503.11984）：语义错误检测基准，对应"找错"这一步，要引用。
- Knowing When to Stop（2607.03991）：研究多次运行的一致性何时收敛，和我们的停止问题相邻，但不涉及修改。
- 记忆或指南类方法已经很拥挤：MAGIC、ZAS-SQL、Mistake Notebook、Memo-SQL、MIRA，不作为主线。

## 精读后的空白判断

| 空白 | 现有最接近的工作 | 结论 |
|---|---|---|
| 用 oracle 阶梯把找错、定位、改写分开量化 | Tyen et al.（通用推理，非 SQL）；Reflective 的粒度表（非 oracle）；Qr-Hint（面向人，待读） | 未见 SQL 上的做法，作为**主实验** |
| 报告翻转率；统计静默错误的占比 | MapleDoctor 报告误修复数，Lin 只报净值 | 可做，作为每个实验都报的指标 |
| 反馈内容消融 | Self-Debug 三档反馈（2023 年模型）；Lin 只比较 R1/R2/R3 | 可做 |
| 修改 vs 重新采样，等算力曲线，加混合方案 | Lin 只比较了 N=5 一个点；ACTS 观察到锁定现象 | 可做 |

以上判断基于 20 篇全文、3 篇精读和 arXiv 关键词检索，不是系统性综述。

## 实验计划（只推理）

**设置**
- 数据：BIRD dev，`data/splits/test.jsonl`。之后加 Spider dev。
- 模型：Qwen2.5-Coder-7B、Qwen3-8B（开思考和不开思考各一组），之后加一个 32B 模型。
- 解码：贪心。每个模型的初始 SQL 只生成一次，所有级别共用。

**X1/X2 反馈阶梯**（代码已写好）：最多 3 轮，每轮记录准确率、错→对、对→错、修改率和 token 数。

| 级别 | 反馈内容 | 对应文献 |
|---|---|---|
| r1 | 只在报错或返回 0 行时给反馈 | Lin R1 |
| intrinsic | 不执行，只让模型自查 | Huang |
| exec | 每次都给执行结果预览 | Self-Debug |
| oracle_bit | 结果预览＋“结果是错的”；对的 SQL 不再给反馈 | — |
| oracle_clause | 再告诉模型错在哪个子句：把该子句换成标准答案的对应子句后结果变对，就认定是它 | Tyen |
| oracle_shape | 再给出正确结果的行数和列数 | — |

**X3 等算力比较**（待写）：在相同 token 预算下，比较贪心＋修改、多采样投票、混合方案（只修改采样结果不一致的题）三种做法，画出准确率随预算变化的曲线。

**X4 方法**（看 X1–X3 的结果再定）：不训练、先门控再定位的修改方法。
